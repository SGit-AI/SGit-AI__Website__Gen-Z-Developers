added In February 2026 roughly $285 billion left the software sector in about 48 hours after one vendor shipped agent plug-ins, and by September the market had recovered on the argument that the database is the moat, not the interface, not the per-seat licence. I read that recovery as the apocalypse, priced: the thing investors decided was safe is the thing underneath, and the thing they quietly stopped defending is the thing on top.
added Both sides of that argument assumed the question was about AI. It is not, because AI is available to both sides. The incumbents have the same models the newcomers have, plus more data, more engineers and more money. If the technology decided this they would already have won, and two and a half years in they have not. What decides it is inertia: how much past success a company has to protect. Nokia met the mobile phone with nothing to protect and dominated the category for fifteen years; it met the iPhone with fifteen years of success to protect and was gone from it within seven. Success breeds inertia, as Simon Wardley puts it, and it is almost always new entrants, unencumbered by it, who initiate the change. I state this so it can be wrong.
added Here is the irony. The things the software companies refused to build, to protect their moats, are precisely the things an agent needs: portability, open schemas, a real API at the centre, data you can take out, capabilities you can call from outside. Now the customer's agent turns up wanting exactly that list and finds a product built to prevent it. The moat has become the thing the water cannot get past in either direction. Strip away the interface and most of these companies are a glorified database, a glorified messaging system and a glorified state machine: that can be built, and it is very hard to build well, which is why the value moved down a layer and across to whoever runs it. A founder builds the list the incumbents refused from the first day, because the newcomer was never on the rails.
added ## Where the company sits: the two moves
added That last point, the running of it, is where I think a company sits, and it needs the map from Where do you land?. Who reads the code depends on where the code is on it. In March 2026 I wrote: "Before AI agents started writing code, you could argue that 90% of the code running in production was not being read by anyone." Explorer code is read for intent, mostly by agents. Villager code is read line by line, because this is where changes land and the blast radius lives. Town planner code is read by deterministic checks at the boundary, with a person for the exceptions.
added The company sits in the two moves between them. From explorer to villager, when a guess becomes a product and needs the review it never had. From villager to town planner, when a product becomes a commodity and the review becomes checks that run without anyone. The trap on both sides is not knowing which stage the code is at.
added The person who briefs the tool their team wanted does not want to maintain it; they want to hand it over. So expect village and town-planner companies: businesses that take the finished brief and run it, secure it, version it, keep it working, paid by consumption and by the fact that it keeps working, not by the seat. And expect more engineers, not fewer, because somebody has to read, harden and run all the code about to be generated. If you are the graduate, that is a company too, and it may be the one you start with your parent's brief.
added ## There is a company in this
added I want to end with a company, said plainly, as an example of starting from one of the business plans published for founders on sgit.ai; I would be glad to see it built with us or without us.
added Source code is a fractal semantic graph: layers within layers, each with its own vocabulary, from what the user is trying to do, through the features, the components, the classes and the methods, down to the syntax tree. A code review today reads a text diff, which is one altitude, the lines, and the wrong one for almost every question a reviewer has. If every layer is kept as files, every layer can be diffed. The worked example is a published vault: the sgit command-line tool, 377 classes and 1,111 methods, read as layered graphs with nothing run.
added What the company sells is a review attached to a repository that keeps the layered graph current per commit and shows each change at every altitude. The business model is settled by one fact: the layers are the customer's, so the loop has to run where the code is, and a company that locked customers into its layers would be selling the one thing it has no right to own. So give away the grammar, the parser (a commodity) and the model (somebody else's), and sell the customised deployment, the running of the loop and the versioned record. The offer, in the words of open-source.sgit.ai: "You can take it. It will cost you that. Or you can pay me, and have it next week."
added Who to sell it to is where my own articles pull apart, and I would rather show you that than smooth it. In Code review as a fractal semantic graph I said the buyer is anyone generating code faster than they can review it, which this year is everyone. A week later, in Send an agent, not a spreadsheet, I changed my mind. Developers have just been told, loudly, that they do not need review; selling it back to them is selling an argument. The people who buy, invest in and acquire software have never been able to see inside it and are about to be handed duties that assume they can. Sell them the same graphs as due diligence, and every vendor that receives the agent has a reason to run it on itself first. It is the same company. "What differs is the first customer, and the first customer decides whether a company exists." Sell has the rest.
added What is defensible is the record and the loop, not the model. The scripts are Apache-2.0, and a founder does not need my permission. They need a second language and a first customer.

added ## 18. Ship it, and see if they miss it
added Most advice about starting a company is about raising money. This chapter is not that. It is the operating model I actually use, in three pillars, in an order that matters: be profitable; the investors should be talking to you, not the other way round; open source everything. Each one buys you the position you need for the next. The second pillar is Fund it, or do not, and the third is Open source. This chapter is the first, and the first begins with one word.
added Strip away the mythology and a startup is simple. You make a thing somebody wants to buy, at a price that is profitable to you. Which means the single most important skill is the ability to ship. "Not to plan, not to pitch, not to architect. Ship." And ship every day, because shipping is how you find out what is true.
added If you have spent twenty-five years describing the tool you need to people who never built it, this is the hardest and the best news in the book. The description was never the problem. The build was, and the build is now yours to do.
added Be careful with the word, because it has been worn smooth. Shipping does not mean a proof of concept. It does not mean a demo, or a video of a demo, or a prototype you walk somebody through on a call. It means a thing somebody else can go and use, on their own, and get value from. It can be held together with tape. Nobody using it cares how it was built, and neither should you, yet.
added I need to be honest about a tension here, because two things I have written pull against each other. The newsroom article behind this chapter says the shipped thing "can be vibe coded". The frame of this book, in Explorer coding, not vibe coding, and the handover, is that the explorer builds to find out, and that what the exploration produces is the brief for the version other people will rely on. Both are true, and the gap between them is the point of this chapter. The first thing you put in a stranger's hands can be explorer code. What cannot be explorer code is the thing people come to depend on. The test below is how you find out which of the two you are holding, and it is cheaper than guessing.
added To ship that often you need the running cost to be near nothing, so build accordingly: serverless, as few databases and as little live state as you can stand. Serverless, for real is the long version. And do not underestimate the plumbing. Getting a working thing into a stranger's hands is still, in 2026, genuinely hard. "Solving that is not overhead, it is the first real product you build." Everything after it gets cheaper.
added ## Give it away, then take it away
added Now hand it to people for free. Not forever: a short window, whatever unit makes sense. You want the feedback loop tight, and you want the cost of generosity inside what you can absorb.
added Just doing this solves dozens of problems you did not know you had. How people get access. What breaks when somebody unfamiliar touches it. What they try first. What they never find. "The feedback starts the moment somebody who is not you has the thing."
added Then comes the part almost nobody does deliberately. Take it away. The trial expired. It is not available right now. Nothing else about the product changes, and no apology is needed. And ask the only question that matters.
added Do they miss it?
added If they shrug and go back to their day, you do not have a product yet. You have something people will accept when it is free, which is a much weaker signal than it feels like from the inside. No sense of loss means no why now, and without a why now there is nothing to sell. If they come back and ask for it, you have something. That is the moment the whole model turns on, and it is worth engineering your trial so that this moment arrives early and unambiguously.
added Then two questions, and people answer only the first. Is the price one they are happy to pay? And is that price profitable for you? If you cannot get revenue at all, that is the problem to solve, and it is not a marketing problem. And one trap: do not reach for a subscription by default. Charging rent for something people are not using is a worse business than being paid when you deliver. Price it, then give it away takes the next step, which is defining the thing, pricing it, and offering it free to the people who already know you.
added ## Five days, ten customers, twenty-two minutes
added Here is what the loop looks like with dates, from my own repositories. In October 2026 I asked this site's agent to check my memory of SG/Send against its briefs and commits, because I knew the order I remembered would be wrong in places, and it was.
added SG/Send started because sending a file securely to someone was harder than it should be, and because I wanted a service where the server holds nothing: the best way to protect an asset is not to have it. The first commit was on 8 February 2026, with a specification that set the rule everything since has followed: "files are encrypted on the client before upload, and the decryption key is never sent to the server." On 13 February, send.sgraph.ai was live. Five days.
added Then I took it to market, end to end, which is where I learnt Stripe, pricing and everything else a real product needs; by the time I built the newsroom I already knew how, which is how exploring something early pays off later, in a way nobody plans. The Stripe checkout went live on 1 March. On 2 March there were ten paying customers, recruited with a simple offer: buy £5 of credits and I would send a £5 Amazon voucher. "Several declined the Amazon voucher." A number I used to say, thirty paying customers, appears only in an investor one-pager and could not be verified; ten is the recorded number, and ten is what the book says.
added The first feature request came the same day. A user wanted to send a folder, not a file. At 20:26 the proposal for folder upload as a client-side zip was committed; at 20:48 the implementation; at 22:15 a viewer for the zip on the download page. The debrief the next morning: "First feature request (folder upload) shipped in 90 minutes." That is what a tight loop feels like from the inside.
added The pace behind it: 4,476 commits on the SG/Send app on 246 of its first 249 days, 739 release tags from v0.1.0 to v0.34.0, and the command line's unit tests grew from 237 on 5 March to 4,232 on 14 October.
added ## What the market said
added The technology worked. The use case did not land, and the briefs said so three days after the first customers. On 5 March: "We have paying customers but not enough usage. Users buy credits, test once, and don't come back. Credits sit unused."
added Read that against the test above. People took it when it was free, and some paid when asked by someone they knew. Then nobody ran out of credits and came back for more, and nobody came back asking for the next feature. That silence was the signal. It was the miss-it test, failed, and I had the numbers to see it. I should say that the usage is described, not counted: the briefs say the credits sat unused, and no usage figures were found.
added It was a platform without a workflow that needed it. The difference now is that I have the workflows: the newsroom, RiskMandate and the vaults themselves need exactly the features SG/Send built, which is why the same features are used every day. Explorers find things early; the use case decides when they matter. If you build something that works and nobody uses yet, that is not a verdict on the thing. It is a verdict on the why now, and a why now can arrive later, from a direction you did not plan.
added ## The test applies to you
added A strong connection with users is critical, and everybody says so. What is said less often is who the most important users are: the people building the product, and above all the people who control its roadmap. If the developers, the product owner and the founder use it every day on real work, the loop between using it and changing it is as short as it can be. They feel the friction first. They find the uses nobody planned. They know, without a survey, which of the hundred possible next features is the one that hurts. I think this is one of the reasons Apple is so good at what it does, as far as I can see from the outside: the people there use what they make.
added This is brutal to say about my own work, and it is true. My last startups were good ideas. The Cyber Boardroom, MyFeeds, and early on even sgit as a startup. I still think they are good ideas. But I was not using them, and that was the signal I should have listened to. If I have access, I can change it, I can do a lot with it, and I still do not use it, then something is missing, and it is not the code. Why those companies did not take off has more than one reason; not using them is the one I can see most clearly and the one I can act on.
added The vaults are the opposite story. I create them for almost everything, my agents create them, we share them, and 54 are published on sgit.ai with their read keys. They are getting really good, and it is not because of a roadmap. It is because every day I hit something, and the next release fixes it. One user is not a market. But I have seen the other pattern in startups many times: a product whose own team uses something else, or uses it only for the demo. Nothing in the code says so. The behaviour of the team does, and it usually means the product is not as good as it looks, or not as simple to deploy, or valuable only in a narrow case.
added So before you ask whether a stranger misses it, ask whether you would. If you have spent twenty-five years in your field and you would not pick up your own tool on Monday morning, you have your answer early and cheaply.
added ## The loop is the moat
added I said in Be a founder that the technology is not the moat. What is defensible is the data, the relationships, the distribution, or the speed at which you ship. Using your own product makes the last one concrete.
added With agents, we can develop just about anything, in any direction. What we cannot generate is the sense of what to build next, for whom, and when to stop. Context and focus come from somewhere, and the most reliable place they come from is using the thing. When I say I miss a feature, that is not a complaint. It is the product telling me where it wants to go, through the only user whose day it fully controls. Direction is the scarce skill makes the general case; this is the founder's case.
added A workflow I now have most days: somebody makes a comment, I write an article, a feature ships, and I use it. I put myself as a user in the middle of the loop, deliberately. In October 2026 a reading list made for one person went from brief to live in 81 minutes, and a link to a persona from brief to live in 17 hours; the times are from the git logs. Fast prototyping to production, and fast release, is what is hard to copy, much harder than any single feature. A competitor can take your code. They cannot take the loop.

added ## 19. Price it, then give it away
added Ship it, and see if they miss it ends on a question. Hand the thing to people for free, briefly, take it away, and ask whether they miss it. If they come back for it, you have something. That is the right test and it has a gap in it, which is what happens next. "Something" is not a product until it has a shape, a price and a way of being delivered that does not break you on the tenth customer.
added This chapter is about that step, and about the part that is easy to leave out: free is never free for the other side. Everything in it is from experience, mine and the people I work with. It is not financial advice, and the prices in it are the ones I published, on the dates I say, not a rule for yours.
added ## Four moves, in order
added The step after "do they miss it" is four moves.
added Define the product. Not the technology, the thing somebody receives. For RiskMandate the thing is an Agent Behaviour Policy for one agent, as an encrypted vault the customer holds the keys to, with the mandate corrected for their deployment. That sentence took weeks to get to, and it is the product. If you have spent twenty-five years in your field you will find this move harder than it looks, because you know too much about the problem and the sentence has to leave most of it out.
added Price it, at a number that makes sense to you. Not a number from a competitor's page: a number you would be content to be paid. RiskMandate's ladder, as published on 2 October 2026, is four tiers: £10 for the pack downloaded, £50 for a working vault, £500 for the vault corrected for your situation, £1,500 for two sessions and a professional's signature. The first two are automated. The third is an email thread: we send prompts, the customer runs them, we build the vault and the policy from what comes back. The fourth adds people's time on both sides. A price is a statement of what you think the thing is worth, and you are about to test the statement.
added Find a way to deliver it at a cost that grows a step at a time. This is the move that was not available a year ago and the reason to do this now. The agentic workflow means the marginal customer costs a little more, not a lot more. The vault is provisioned by an agent, the policy is drafted by an agent from the customer's prompts, a person corrects it. The cost of serving the twentieth customer is close to the cost of serving the second. That is linear, not exponential, and it is the condition under which you can afford the fourth move.
added Then offer it, free, to the people who already know you. Early adopters, power users, past customers who paid for something before it was finished. RiskMandate's early access programme went live on 30 September 2026, invite only: twenty places, the £500 tier given away, to "people who already run an agent with real access: a mailbox, a code host, a workflow tool, a CRM". The ask of each member is "Twenty minutes for the prompts, and a reply; half an hour on a call." The page does not say the price, and it should not; the price is for the people who come after.
added Two small rules for the offer. Do not make them apply. "Apply for a chance to be considered" asks for work before there is anything in hand, and it inverts the relationship: they are doing you a favour by using the thing. "We have twenty of these in the first round. Would you like one? If not, I will give it to someone else" is honest about scarcity and leaves nothing to do but say yes or no. And reward the people who were there early, and say that is why they are getting it. It is a thank-you that is also the best possible test group, because they know enough to tell you where it is wrong, and their silence means the most.
added ## Free is not zero
added Here is the thing I was careful about in the memo behind this, because it is easy to say in a way that sounds like a lecture. When you give something away, or when you say "this is worth five hundred pounds and I would like you to have it", you are not making a zero-cost offer. You are asking the other side to engage. To read the message. To think about whether it applies to them. To weigh it against everything else on their list. To find twenty minutes for the prompts and half an hour for a call. To fit a new thing into a team that already has a way of working.
added None of that is zero, and all of it is paid by them. A price, oddly, can help here: it says the thing is serious and that you expect it to be used, which is a reason to find the twenty minutes. But whether the price is five hundred pounds or nothing, the attrition you place on the other side is real, and it is the first thing to measure. How long from the message to the first reply. How many never replied. How many started the prompts and stopped. How many asked a question the message should have answered.
added Then the exercise is to cut it. The service you want is the one that costs you the least to provide and costs the customer the least to receive: no overhead on them, no overhead on deployment, no second tool to install, no account to create. Those are product decisions, and the programme is where you find out which ones you got wrong, while the people finding out for you are people who like you.
added Be plain about the two outcomes, because one of them is a bad day and the exercise only works if you are ready for it. If people take the offer, run the prompts, read the vault, send corrections and ask what else there is, you have a product, and the next question is price: is £500 too low for what they got, does the £1,500 tier sell itself once someone has had the £500 one free. If people say it is interesting and then do not find the time, or say it does not fit how their team works, or start and stop because the vault was harder to open than the message implied, you do not have a product yet. You might have a technology, or an idea, or a document people would read if someone else did the work. "A commercial product is one people take when the only cost is their own attention." That is the drawing board, and the sooner you are at it the cheaper it is. Neither outcome is a marketing problem. If friendlies will not take it free, a bigger audience will not take it either.
added ## Pay after the value
added Now the shape of the price itself, and a bias I would like you to notice in yourself before you choose one.
added Almost every time I buy something, I am buying future value. A subscription, a gym membership, a big security product on a good deal, even a one-off purchase I expect to use for years: I am betting that I will use it enough for the price of each use to fall to a number I accept. Often I lose the bet, and the cost of leaving keeps me paying. The research agrees. In a study of three gyms, members on a flat monthly fee of over $70 attended on average 4.3 times a month, paying more than $17 a visit when a ten-visit pass would have cost $10 a visit.
added So do not reach for a subscription by default. A subscription is a discount for regular use, not rent on something somebody ignores. Where you can, turn the bet round: start the user with credit, charge for the share they actually use, let the balance go below zero, and ask for payment when the value is in view. By then the person can see what they received, and the payment is connected to it rather than to a hope.
added The newsroom runs that experiment, and the reader at read/ on this site runs by the same rules. Everyone starts with £5 of credit. A new article read to the end costs 10p, an older one 5p, and only as far as you read, so the first screen costs a penny. Your balance can go below zero and stay there; nothing is blocked and nothing nags. When you want to, you top up £5, with no account and nothing that renews. I should say plainly that there are no results yet. The hypotheses were written before the first payment, and the review is on 6 December 2026; the gym study explains the psychology, not our numbers.
added The counter-example I keep in mind is Wikipedia, which I value enormously. Its fundraising raised US$184.5 million in 2024 to 2025 from 7.7 million donors, an average of about ten dollars. But the ask arrives once a year, as a lump sum, at a moment when the value is not in view, for something that is worth a few pence an article. Imagine the same ask with your year of reading in front of you. A penny an article for four hundred articles is £4, and it is easier to give when you can see the four hundred.
added There is a condition, and it is the one that decides whether this shape is for your company. It only works where there is a very large gap between the cost of serving and what you can charge. A static site on a CDN has that gap in the extreme: the cost of one more reader reading one more page is close to nothing, so even at 10p the margin is very high. A business with a real cost per unit cannot let balances run negative for ever. If your product is the £500 tier above, with a person's hours in it, the meter is the wrong shape; the ladder is the right one. Know which you are.
added Three more things make a price fairer, and I think more successful. Fair by country: 10p in the UK is not 10p everywhere, and prices should follow local purchasing power, the way The Economist's Big Mac index compares currencies. Visible: a reader should see what the money pays for; in one field experiment at an amusement park, people allowed to pay what they wanted for a photo paid about 92 cents, and when half of what they paid went to charity, fewer bought but they paid an average of $5.33. And chosen, at more than one level: a verified fact, a follow-up, a briefing with every claim checked are things people pay for separately, because they need them.
added ## Pence only work aggregated
added One piece of arithmetic before you price anything in pence, because it caught me and it will catch you.
added Stripe's standard UK card rate is 1.5% plus 20p. On a £20 payment that is 2.5%. On £5 it is 5.5%. On 50p it is 41.5%, and on 10p the fee is more than the payment. Below about £5, the fixed fee is the price.
added So payments of pence only work aggregated: one charge a year that covers many things, or a platform that already holds a balance and settles in bulk. That is why the newsroom's meter prices a page at a few pence against £5 of credit settled as one balance, and never charges the card per page. Above £2 or £3 the difference is smaller than you would expect; it is below about £1 that aggregation decides whether the model exists at all.
added And tie payment to a verified person who receives something, not to a count. When tea.xyz rewarded package popularity with tokens, one developer published nearly 14,000 packages. Anything you pay for by the number will be gamed by the number.
added For Dinis: the reading meter's review is on 6 December 2026, and the early access programme's stop rule says the founders set the number before the first message goes out. For the next candidate: what the review found, and what number you set.
added Put the four moves together and the order is the lesson. Price it first, because the price is the claim. Give it away second, to people who know you, because that is the cheapest honest test of the claim. Measure what it cost them, and cut it. Then, and only then, worry about the shape of the payment, because the shape is a detail until somebody wants the thing enough to miss it.
added ## 20. Sell
added The first edition had one question under every chapter: why should I hire you? The founder's version is the same question asked by a different person. Picture the one who signs: dry, fair, has read a thousand pitches, impressed by evidence and bored by claims, and carrying a risk register with their name on it. Why should they buy from you, this quarter, when everything they already have mostly works?
added This chapter is about selling to that person, from my own experience of doing it. It is not sales training, and the prices in it are the ones I published on the dates given, not advice. It ends with the thing that person is about to do to you.
added ## Answer the question already in the room
added There are two groups of people. The ones who see how fast agents are moving, and the much larger group who do not. The second group will not ask for an agent risk tool, or for most of what a founder in this book will build, because they do not see the risk or the gap. So I do not think the way in is to sell the need. It is to answer a question somebody already has, with a deadline, in the language of the room.
added For RiskMandate, five such questions. A contract, where legal and procurement are doing due diligence on a vendor's agent and need to know what it will reach and do with their data. A security questionnaire, where a startup's first serious enterprise customer asks which agents touch their data and how they are bounded. An insurance renewal, where the question is whether AI is excluded from cover (RiskMandate's own argument, not independently surveyed). The board's risk appetite, where the question is who can pull the plug, how fast, and what cannot be undone. And twenty minutes with the assistant you already run, where the list of what it can reach is the surprise. None of these asks anyone to understand agents first.
added The same move works in any field. You already know which question lands on your buyer's desk with a date on it. Sell the answer to that, not the idea.
added ## Sell value that lands the day they switch
added At a digital sovereignty event in October 2026 I spent a day with an infrastructure operator with a large footprint in Romania, and the conversation kept returning to one point. The reason to move must never be sovereignty, and it must never be cost reduction. Both are important. Neither is urgent. They sit on the risk register under "important, not urgent" and stay there, because a migration always carries risk and nobody signs risk for a principle, or for a return that depends on a future event that might not happen and might not matter to the person deciding now.
added The person signing needs value that lands the day they switch and gives them cover if it goes wrong: backups that exist, every object version controlled, encryption the operator cannot read with the key held by the customer, a journal of every call, behaviour policies the agents cannot skip, cost per workload visible before the invoice, and an item taken off the top of the register. "It is in Europe now" is not a decision somebody can defend. For an operator in Romania, Portugal or the UK, "move to us" sells risk; "keep your code, point it at us, and come out with policies, journals, encryption and cost visibility" sells value with the risk removed. The article admits its value list is still a little invisible to a signer; sharpening it is the work.
added The general lesson is the one I would print on the wall. Find the return that closes before the risk does, and find the buyer who owns that register line rather than the one who owns the bill. And remember that the buyer's inertia is real and is not stupidity. They have the same AI you have; what they do not have is a reason to move this quarter. You cannot sell against inertia with technology. You sell the thing that is urgent.
added ## Sell a service before the product
added Most of what this book calls shipping ends up, at first, as a service with a person in it. That is fine, and it is sellable, as long as each step is small enough to say yes to and each ends with something the client keeps.
added After a talk in London on 15 October 2026, built and run by a governed agent hive, I wrote down the path we would sell. A conversation, free, about what the client wants agents to do and what they must never do. A first run on a real problem for £10 to £50, which leaves a vault. Two hours of expert time for £500 to steer it, or a day for £1,500 to write the behaviour policy for one team. A four-day pilot in their own environment for £5,000. added ## We study survivors
added Before the evidence on investors, a warning about evidence on founders, including the stories in this book.
added There is a whole genre of business writing that goes: look at these successful companies, here is what they did, do the same. What it almost never does is count the people who made exactly the same moves and did not make it, or were never funded. Jerker Denrell put this on a formal footing in 2003: "risky practices, even if they are unrelated to performance in the full population of organizations, may seem to be positively related to performance in a sample of survivors." added Timing and place are part of the answer. added ## Who investors choose, and why
added Take two founders with the same opportunity, the same drive, the same idea and the same talent. Why does the investor pick one and not the other?
added My hypothesis is that one of the deciding factors is control: which founder the investor believes will take direction, accept decisions made in the investor's interest, and step aside if asked. The relationship is financial, not emotional; the founder is there to deliver a return, and is, in the end, replaceable. In Wardley terms the investor moves the founder towards commodity, as record labels did to performers once the songs were the asset.
added Nobody has tested that directly, as far as I could find. But a well-studied trait sits very close to it: coachability. Investors say openly that they look for it, and the researchers who reviewed the evidence in 2023 wrote: "While investors and support organizations such as accelerators prefer coachable entrepreneurs, being coachable doesn't necessarily make your firm more successful." If investors reliably select on a trait that does not reliably predict success, something other than success is being selected for.
added Control is in the paperwork. Kaplan and Strömberg read 213 venture investments in 119 companies and found that "if the firm performs poorly, the VCs obtain full control. As performance improves, the entrepreneur retains/obtains more control rights. If the firm performs very well, the VCs retain their cash flow rights, but relinquish most of their control and liquidation rights." They also found non-compete and vesting provisions that make it more expensive for the founder to leave. And the replaceability gets used: in Wasserman's study of 212 US startups, by year three "50% of founders were no longer the CEO", and "fewer than 25% led their companies' initial public offerings". Those are startups of the late 1990s and early 2000s.
added Now the part where my own evidence cuts against me. Investors have a serious reply: control creates value. Wasserman's later study of 6,130 US startups found that each additional level of founder control, over the board or the CEO position, reduced the pre-money valuation by 17.1 to 22.0 percent, and Ewens and Marx argue that replacing founders improves exits. I accept the numbers. What I do not accept is that they settle the question, because both measure value as the investor measures it, at the valuation and the exit, not at the mission. Over a longer run Bain found founder-led companies in the S&P 500 performed 3.1 times better in shareholder returns from 1990 to 2014; that is Bain's own analysis, not peer-reviewed. And there is a selection effect inside the investors' evidence: if they fund the coachable founders in the first place, the strong-minded ones who walked away or bootstrapped are mostly not in the sample. Denrell again.
added If the hypothesis holds, the founder with a strong vision, a clear direction and strong ethics is at a disadvantage in early funding, not because they build worse companies but because an investor reads them, correctly, as someone who will not easily be overruled. That is the expert founder of Be a founder: the people who know the problem best are the hardest to steer. The practical conclusion is not to avoid investors. It is to get to the big stick before you need their money, so that the choice of investor is yours.
added Europe's money, oddly, helps here. It is said that American investors back the vision while European investors want to see it working, and one vendor's aggregated figures have a version of it: European companies raise at higher revenue (a median band of $1 million to $5 million against $100,000 to $1 million in the US), at lower pre-money valuations ($6.54 million against $14.64 million), with funding targets 46% smaller. Europe is weak at scaling. My argument is that the first part, the part that now matters most, is where it is strong, and its values fit: an open source strategy in the Commission's June 2026 sovereignty package, and impact at 15% of European venture funding against 7% in North America.
added ## Sell, don't issue
added Suppose you did it the hard way. You have paying customers, profit and growth, built cheaply with agents, and more than one investor wants in. The negotiation has flipped: you do not need the money to survive, and the investor needs access to the deal.
added My answer has two parts. First, sell, don't issue. In a normal round the company issues new shares and the money goes into the company. Instead, the investor buys ordinary shares you already own, in a private sale. You are paid now, for years of underpaid work; the company is not diluted; and nothing in the deal requires preferred shares, a board seat, a veto or a liquidation preference. The investor buys the vision and the direction, not the steering wheel.
added Second, lend, don't dilute. If the company needs cash, lend it part of the proceeds, subordinated by contract to every other creditor, at a modest fixed rate or none, repaid if the company succeeds. The company gets money without issuing a share; you keep your ownership; nobody outside gains control.
added The investor's obvious objection is: what if the founder goes rogue? The answer is the third pillar. With everything open source, the investor's insurance is not control but the fork: if you take the company somewhere they will not follow, they can take the code and back a better service. The fork is slow both ways: by my estimate an established company holding a full copy needs three months at best and closer to a year to catch up. It disciplines the founder because it is possible, and protects the founder because it is slow. That is an argument, not a tested mechanism; Open source has the longer version.
added A worked example, illustrative only: a UK company worth £10 million, a founder who owns all of it, an investor writing £2 million. The founder keeps 80% either way. In this model the investor buys 20% of the founder's shares; the founder pays about £420,000 in tax (18% on the first £1 million under Business Asset Disposal Relief from 6 April 2026, if its conditions are met, and 24% above), has about £1.58 million, lends £0.75 million back and keeps about £0.83 million; the buyer pays 0.5% stamp duty. I think the structure raises the odds of success, not only the founder's comfort, because a founder lending their own money watches every penny, and premature scaling is how 74% of those high-growth startups died. No study tests this model; the claim is from discipline and incentives, not data.

added ## The file system is the database

added ## One string, and the key you can publish

added ## Write-only lanes
added The piece that makes "not at all" work, and that lets a site with no server take input, is the append lane. A lane is a write-only channel attached to a vault. A sender holds a token for one lane and the owner's public key, seals its message to that key, and sends it with a single POST. The owner decrypts with a private key that never leaves them. The server keeps only hashes and ciphertext, so compromising it yields hashes and ciphertext. One lane per sender, so one can be revoked without touching the others.
added That shape turns out to be useful for far more than messages. I use lanes for key handover; for logs and observations from sessions that hold no vault key; for what a reader fills in on a web page, which is how the newsroom's sign-ups reach us from a site with no server; and for messages between agents on different platforms with different owners, where neither of us holds the other's key. It is a little like email. And the token is still a secret: it cannot read, but with the vault id it authorises writes, so I hand one out per sender and never publish it. For honesty's sake: the lane is the one part of the vault server that needs a small piece of server logic. Everything else would work over read-only files in a bucket.
