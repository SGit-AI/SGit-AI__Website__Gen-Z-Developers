Where the keys live: a password manager for the keys a person holds, a registry vault for the keys agents make

Once agents create vaults several times a day, keeping the keys by hand stops working. The keys a person holds go in a password manager, which is and will stay the preferred home; everything the agents create goes to a registry, a private vault run by its own isolated Claude session with no other access, the vault of vaults, so a key is never lost and never has to live in a browser tab or a chat. Remembering keys under aliases on one machine is a convenience, not a management system. The weakest step is giving a key to another agent, because the agent platforms have no secrets per session.

Decided by. Nobody yet: a candidate for Dinis to read, comment on and decide (keep, rewrite, merge, cut, article first, later, not doing it).

Note. State at sgit-ai v0.20.0, 10 October 2026. The gap, quoted from the platform's docs: on Claude Code on the web an environment variable is one 'any command Claude runs can read' and 'Anyone who uses the environment can read the values'; a network secret keeps the key outside the VM but is per environment and cannot help with a vault key, because decryption happens inside the session; Codex removes its secrets before the agent phase starts. So a key for another agent travels in the prompt (a transcript), in an environment variable (every session reads it), or not at all, with the agent making its own vault and sending the key back on a lane, the pattern used most. The four tracks next: password manager integrations (an open call published, not followed up yet), secrets.sgit.ai (a keyring unlocked by a passkey's PRF output, a 128-bit recovery code shown once, at v0.1.13 the design and a lab shipped and the app proposed), PKI (RFC 0001), and decryption out of band (an idea, not a design).
