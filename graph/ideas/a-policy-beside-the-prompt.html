A third input: a behaviour policy beside the system prompt and the prompt, which the vendor acknowledges, enforces where it can and answers for

An agent today gets a system prompt from its vendor and a prompt from us; it should also take an Agent Behaviour Policy, written to a published standard, which the vendor accepts as part of the deployment, enforces as far as the platform can see, reports every breach against the same day and, eventually, carries liability for the rows it accepted. The user answers for what is outside the policy and the vendor for what is inside it, which is a better model than the user being liable for everything because they clicked allow. Most agents already run a hidden policy of their own (Claude in Chrome will not type a password), and a system prompt is a light behaviour policy not written as one; the layering is the vendor's published policy, then the deployer's, with the business logic only the deployer can write.

Decided by. Nobody yet: a candidate for Dinis to read, comment on and decide (keep, rewrite, merge, cut, article first, later, not doing it).

Note. A proposal: the article says no vendor accepts a behaviour policy as an input today in this sense; Claude Code's permission rules and managed settings are the nearest thing and cover settings, not business rules. Liability per row is the end state, not the start; acknowledgement and breach reporting can come first.
