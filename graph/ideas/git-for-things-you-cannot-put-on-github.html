Git for things you cannot put on GitHub: what an encrypted vault is

There is a category of file with nowhere good to live: a risk register with real system names, an analysis still being argued about, the working memory of an agent that has read your codebase for a month, client material under NDA. It wants history, branches, diffs and a link, and it is the reason people say 'we can't put that in GitHub', so it ends up in a shared drive or a thread nobody can diff. sgit is git for those files: encrypted before they leave your machine, versioned like git, stored on a server that holds ciphertext and nothing else, not filenames, not directory structure, not commit messages. There is no key escrow, no admin override and no support engineer who can recover it, which is a feature with a real cost.

Decided by. Nobody yet: a candidate for Dinis to read, comment on and decide (keep, rewrite, merge, cut, article first, later, not doing it).

Note. Dated 25 August 2026. The evidence in the article: an object is 786 bytes of AES-256-GCM ciphertext named by the SHA-256 of the encrypted bytes, so the host can deduplicate it, cache it and serve it from a CDN without knowing what it is; all nineteen published vaults cloned from their published keys, 1,389 files, no failures. Underneath it is real version control (multi-parent commits, a tree per directory, merge-base, three-way merge), not a sync folder. Status, plainly: sgit is beta and says so on every page; pip install sgit-ai, pure Python, two runtime dependencies, Apache-2.0.
