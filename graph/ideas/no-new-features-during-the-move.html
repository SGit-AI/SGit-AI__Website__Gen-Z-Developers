A villager move: no new features while you move, or nobody can tell which change broke what

A migration is a pure villager move, from explorer to town planner: take something that works and make it boring, reliable and cheap, without changing what it does. The temptation to add features during it is the moment everything derails, because the migration is now also a product change and nobody can tell which of the two broke what. The argument that the move is what allows the features is right, and it is exactly why the two must not be mixed: move first, with the code unmodified and the twin adding its value underneath, then add the features the move made possible.

Decided by. Nobody yet: a candidate for Dinis to read, comment on and decide (keep, rewrite, merge, cut, article first, later, not doing it).

Note. The same rule the newsroom used for its own explorer-to-villager move (green-does-not-mean-live cites it): same bytes and same bugs first, features after. Could sit in shipped-means-the-user-has-it instead.
